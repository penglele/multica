# Channel 协作工作台扩展方案

## 1. 文档定位

这份文档是 `channel-chat-upgrade.md` 的**下一阶段计划**。

执行顺序要求：

1. 先完成 `multica/docs/plan/channel-chat-upgrade.md`
2. 等频道聊天主链路稳定后，再进入本文

本文不替代前一份文档，而是在其基础上继续把频道从“成熟聊天”升级为“可持续协作的聊天工作台”。

---

## 2. 为什么要做这一阶段

`channel-chat-upgrade.md` 解决的是：

1. 能顺畅发消息
2. 能清楚知道有没有触发 agent
3. 能看到发送状态、处理中、失败、未读、分页、断线恢复

但当聊天真正变多之后，还会出现另一类问题：

1. 我今天该先看哪些聊天？
2. 哪些消息专门在找我？
3. 哪些关键信息值得留存？
4. 某条关键结论怎么精准发给别人？
5. 群里这个 agent 到底是谁、适合处理什么？

所以第二阶段要补的是**聊天的管理能力、引用能力、留存能力、对象理解能力**。

---

## 3. 本阶段目标

在不破坏已完成频道聊天体验的前提下，补齐以下 5 类能力：

1. **Inbox**
   - 把“需要我处理的聊天”聚合到一个入口
2. **Saved**
   - 收藏重要消息，避免聊天内容淹没
3. **全局提及**
   - 把整个系统内 `@我` 的消息集中起来
4. **消息链接**
   - 每条消息都可以被准确引用和跳转
5. **对象详情面板**
   - 点击 agent / 用户即可看到它是谁、能干什么、当前状态如何

---

## 4. 范围边界

### 4.1 本轮必须做

1. Channel / DM / Thread 统一进入 Inbox
2. 全局未读 + 全局提及聚合
3. 消息收藏列表
4. 消息永久链接
5. Agent / User / Machine 详情侧栏

### 4.2 本轮不要做

1. 全文搜索
2. 高级筛选器构建器
3. 复杂权限编排
4. 自动摘要周报
5. Slack 级消息规则自动化

---

## 5. 五项能力的产品定义

## 5.1 Inbox

Inbox 不是另一个聊天页，而是“我当前应该关注的聊天条目列表”。

每一行条目应至少展示：

1. 来自哪个频道 / 私聊 / 线程
2. 最新消息摘要
3. 最新发言人
4. 是否未读
5. 是否提到我
6. 最后活跃时间
7. 是否已处理

用户动作：

1. 打开某条条目并跳到对应聊天位置
2. 标记已读
3. 标记未读
4. 标记 done，从 Inbox 主列表收起

### 5.2 Saved

Saved 是“个人收藏消息列表”。

每条收藏至少应展示：

1. 原消息内容摘要
2. 所在频道 / 线程
3. 原发送者
4. 收藏时间
5. 打开原消息
6. 取消收藏

### 5.3 全局提及

全局提及是“所有明确叫到我的消息集合”。

来源包括：

1. 频道内 `@我`
2. 线程内 `@我`
3. 私聊内直接点名

注意：

1. 它不是简单的 Inbox 过滤器实现细节，而是用户可感知的一类工作流
2. 在 UI 上可以作为 Inbox 的一个 filter，但数据上必须能稳定算出 `has_mention`

### 5.4 消息链接

任何一条消息都必须能生成稳定链接。

能力要求：

1. 复制消息链接
2. 打开链接后能进入对应频道 / DM / 线程
3. 能尽量定位到具体消息
4. 若该消息已不在当前页面缓存中，要自动补拉附近历史

### 5.5 对象详情面板

聊天里出现的对象至少包括：

1. User
2. Agent
3. Machine（如果当前产品语义里已存在）

点开后应至少展示：

1. 名字
2. 头像
3. 身份类型
4. 简介
5. 状态
6. 最近活跃
7. 可执行动作入口
   - 发起对话
   - 查看资料
   - 在频道中 @ta

## 6. 与第一阶段的依赖关系

本文默认以下能力已经完成：

1. 频道消息发送、失败、重试、处理中状态
2. 频道未读与增量补拉
3. 频道消息结构化目标和稳定消息 id
4. `ChannelPanel` / `ChannelDetailPage` 的主体能力已统一或至少行为一致
5. 实时推送与断线恢复已经可用

如果上述能力未稳定，不应提前进入本文实施。

## 7. 数据模型建议

## 7.1 Inbox 条目

建议新增聚合表或聚合查询层，统一表示“一个待关注对话条目”。

建议字段：

1. `id`
2. `user_id`
3. `entry_kind`
   - `channel`
   - `dm`
   - `thread`
4. `channel_id`
5. `parent_channel_id`
6. `parent_message_id`
7. `latest_message_id`
8. `latest_message_preview`
9. `latest_sender_id`
10. `latest_sender_type`
11. `last_activity_at`
12. `unread_count`
13. `has_mention`
14. `done_at`

如果已有 `inbox_entries` 表，可优先复用，不必重复造表。

## 7.2 Saved

建议新增：

1. `saved_message`
   - `user_id`
   - `message_id`
   - `channel_id`
   - `created_at`

注意：

1. 如果消息体系分 chat / channel / dm，要先统一消息引用格式
2. 不要让 saved 只支持某一种消息场景

## 7.3 Mention 索引

可以通过消息入库时同步写聚合信息，或用查询实时计算，但必须稳定提供：

1. 当前用户是否被提到
2. 首条未处理 mention 是哪条
3. 某条对话里 mention 未读数是多少

## 7.4 消息 permalink

建议统一消息引用结构：

1. `route_kind`
   - `channel`
   - `dm`
   - `thread`
2. `channel_id`
3. `message_id`
4. `thread_parent_message_id`（如适用）

## 7.5 对象资料

Agent / User / Machine 详情优先复用现有实体资料接口。

如果资料不够，补字段时优先补：

1. 展示名
2. 头像
3. 简介
4. 当前状态
5. 最近活跃时间

---

## 8. 前端落地方案

## 8.1 新增主入口

建议新增以下页面或面板：

1. `InboxPanel`
2. `SavedPanel`
3. `DetailPanelHost`

## 8.2 Inbox UI

至少具备：

1. `All`
2. `Unread`
3. `Mentions`

每一项点击后：

1. 跳转到对应聊天
2. 尽量定位到首条未读或命中消息

每一项右侧操作：

1. Mark read
2. Mark unread
3. Done

## 8.3 Saved UI

至少具备：

1. 收藏列表
2. 打开原消息
3. 取消收藏
4. 复制消息链接
5. 复制消息内容

## 8.4 消息操作菜单

为了支持 Saved / 链接，消息卡片需要补操作菜单：

1. 收藏
2. 取消收藏
3. 复制链接
4. 复制内容
5. 跳到原线程

## 8.5 对象详情面板

点击头像或名字时打开侧栏，不中断当前聊天上下文。

面板要求：

1. 支持 agent / user / machine 三类展示
2. 统一壳子，不同类型只替换内容区
3. 支持从消息列表、成员列表、Inbox 条目进入

---

## 9. 后端落地方案

## 9.1 Inbox 聚合接口

建议新增：

1. `GET /api/inbox`
2. `POST /api/inbox/{id}/read`
3. `POST /api/inbox/{id}/unread`
4. `POST /api/inbox/{id}/done`

支持参数：

1. `filter=all|unread|mentions`
2. `cursor`
3. `limit`

## 9.2 Saved 接口

建议新增：

1. `GET /api/saved`
2. `POST /api/messages/{messageId}/save`
3. `DELETE /api/messages/{messageId}/save`

## 9.3 消息链接解析

建议补：

1. 消息 permalink 生成 helper
2. 路由解析 helper
3. 按 message id 定位的消息查询接口或复用现有增量拉取

## 9.4 对象详情接口

若现有资料接口不足，新增轻量聚合接口：

1. `GET /api/agents/{id}/profile`
2. `GET /api/users/{id}/profile`
3. `GET /api/machines/{id}/profile`

---

## 10. 实时与状态策略

## 10.1 Inbox 更新

以下事件应推动 Inbox 刷新或增量更新：

1. 新消息进入
2. 未读变化
3. mention 变化
4. done 状态变化

## 10.2 Saved 更新

以下动作应本地即时响应：

1. 收藏
2. 取消收藏

## 10.3 链接跳转

用户打开消息链接时：

1. 先进入正确的聊天场景
2. 如果当前页没有目标消息，则拉取附近历史
3. 成功定位后高亮目标消息

---

## 11. 分期建议

推荐顺序：

1. **E1：消息链接 + 消息操作菜单**
2. **E2：Saved**
3. **E3：Inbox / 全局提及**
4. **E4：对象详情面板**
5. **E5：跨面板联动与细节打磨**

原因：

1. 链接和消息菜单最独立，风险最低
2. Saved 依赖消息菜单，但不依赖复杂聚合
3. Inbox / 全局提及最有价值，但涉及聚合、未读、排序、done 状态
4. 对象详情面板最后做，更容易复用前面产出的跳转和展示信息

---

## 12. Claude 执行说明

### 12.1 前置条件

开始本文前，先确认：

1. `multica/docs/plan/channel-chat-upgrade.md` 已完成
2. 频道聊天的发送、未读、断线恢复已经稳定
3. 结构化目标字段已经落库并在前后端贯通

### 12.2 执行原则

1. 不要回头打乱第一阶段已稳定的聊天主链路
2. 不要先做大全局重构，先从消息菜单与链接切入
3. 任何 Inbox 聚合都必须先定义“唯一条目 id”与“未读更新规则”
4. Saved / Inbox / Mentions 必须同时支持 Channel、DM、Thread，不要只做单一场景
5. 详情面板优先复用现有资料接口和现有右侧抽屉壳子

### 12.3 完成标准

以下同时满足，才算本文完成：

1. 用户可以把任意消息收藏并在 Saved 中重新打开
2. 用户可以复制任意消息链接并精准跳转
3. 用户可以在一个 Inbox 中看到 All / Unread / Mentions
4. 用户可以把一个 Inbox 条目标记 done
5. 用户点击 agent / user / machine 后能看到清晰资料面板

---
